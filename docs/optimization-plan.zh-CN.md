# GitSeek 优化计划：从完整功能到可验证的开源贡献闭环

制定日期：2026-10-28

状态：阶段 A（A1–A9）工程实现及项目代码回归已完成；全目录历史脚本 lint 例外见实施记录。其余阶段待实施。
目标：在投递简历前，提升项目的正确性、评测可信度、任务可靠性和实际使用价值。

## 1. 下一阶段的产品目标

让用户完成一条可追溯的路径：

> 描述需求 → 筛选仓库 → 选择可参与的 Issue → 查看证据与难度 → 生成修复补丁 → 查看独立验收结果。

重点产出是一套可复现的检索评测、一组真实 Issue 修复实验、一次用户试用，以及可以展示成功与失败的演示材料。

本计划先聚焦公开 Python 仓库。自动向上游提交 PR 不作为默认流程；补丁先由用户审查。

## 2. 当前起点与证据边界

以下依据当前工作区代码及已有实验文档整理：

- 已实现约束解析、多路召回、RRF 融合、特征重排、证据档案、贡献 Issue 筛查和缓存降级。
- 已有 tree-sitter 切块、代码定位、修复循环、Docker 沙箱和 PostgreSQL 任务队列的初步实现。

## 3. 阶段顺序与进入条件

工作量仅用于安排顺序，实际进度受模型预算、容器环境、独立标注者和试用者时间影响。

| 阶段 | 优先级 | 主要交付 | 进入条件 | 参考工作量 |
| --- | --- | --- | --- | --- |
| A. 执行与验收修正 | P0 | 可靠的工具执行、固定版本、独立验收 | 可立即开始 | 3–5 个工作日 |
| B. 检索评测升级 | P1 | 新语料、盲评、冻结测试集、基线报告 | 可与 A 交错准备 | 5–8 个工作日及人工标注 |
| C. 修复实验与消融 | P1 | 真实 Issue 清单、逐例结果、失败分析 | A 验收通过 | 5–8 个工作日，按预算分批 |
| D. 性能与任务恢复 | P2 | 性能基线、租约恢复、取消与幂等 | A 完成，可与 B/C 交错 | 4–6 个工作日 |
| E. 产品试用与交付 | P2 | 完整主路径、试用记录、演示及报告 | 主路径稳定，已有可信实验 | 3–5 个工作日及招募时间 |

执行原则：每个阶段先保存基线，再修改实现，最后记录差异。阶段验收未通过时先解决原因，不通过调整标签或删除失败样本制造提升。

- [x] A4. 扩展评测实例身份：修复前 commit、环境/镜像标识、依赖锁定、测试入口、数据集与模型配置版本。

- [x] A7. 验收测试由评测方持有，避免被 Agent 修改；补丁涉及受保护测试时明确拒绝或进入人工审查。
- [x] A8. 保存逐步 trace、最终 diff、测试命令、真实退出码、日志、用量和失败原因；未知费用不能显示为已确认的零费用。
- [x] A9. 对上述行为补充必要回归测试，并检查现有协议与状态字段是否需要同步迁移。项目源代码检查通过；工作区原有未跟踪报告脚本的全目录 lint 问题单独保留，不视为已修复。

### 验收

- 同一轮每条工具动作只执行一次，覆盖有副作用命令与补丁操作。
- 仅输出 FINISH、空补丁、测试缺失、测试超时、非零退出码均不能被计为已验证修复成功。
- 已知失败样例在基准版本失败，正确补丁应用后通过；无效补丁不会通过验收。
- 同一实例能用固定 commit、环境和配置重复运行，并找到完整证据。
- 不要求不同模型运行生成完全相同的补丁；复现要求明确区分固定输入与模型随机性。

### 任务

- [ ] B1. 保留历史 v2 数据与结果，新建数据版本；首轮目标 300–500 个时间戳固定的仓库、150–200 条查询。

- [ ] B3. 加入无合适结果的查询，区分明确不满足、无法确认和可以满足。
- [ ] B4. 按意图/近似查询分组划分开发集与冻结测试集；测试标签不进入调参过程，仓库与技术栈分布分别报告。
- [ ] B5. 使用独立候选池构建标注包，覆盖各基线候选和困难负例，避免只标注当前系统偏好的结果；报告标注覆盖和未标注结果处理规则。
- [ ] B6. 邀请第二标注者盲评 20%–30% 的查询对应候选池，报告覆盖率、加权 Kappa、分歧及裁决记录。没有独立标注者时保持待办。
- [ ] B7. 对比全文/关键词、本地特征向量、RRF、最终重排；外部 embedding 作为预算允许时的独立实验。
- [ ] B8. 同候选池实验用于隔离排序作用；另设端到端实验评估召回链路，避免混淆两种结论。
- [ ] B9. 增加硬约束违反率、证据不足率和无结果处理指标，同时报告 Recall@10、nDCG@10、MRR@10 及置信区间。
- [ ] B10. 预先冻结主指标、约束底线和可接受退步范围；最终测试集仅用于方案确定后的报告。

### 验收

- 数据、标注规则、划分、候选快照和代码版本均可追溯，旧版本保持可复现。
- 报告包含分桶表现、失败样本及各基线；不以新旧不同语料的分数差宣称提升。
- 明确约束有证据可判断时正确过滤；证据不足时显示未知，不冒充严格满足。
- 达不到独立复核、覆盖或提升门槛时如实记录，不预设必须超过现有 91.0%。

## 6. 阶段 C：真实 Issue 修复与消融

### 任务

- [ ] C1. 先用 3–5 个真实 Issue 验证环境和验收流程，再扩展为 10–20 个冻结实例。
- [ ] C2. 每个实例绑定修复前 commit、缺陷测试、环境及 gold 文件；gold 补丁、修复提交和后续讨论不得进入 Agent 输入。
- [ ] C3. 固定模型、提示词、工具、预算和配置，先跑基线，保留全部失败实例。
- [ ] C4. 比较关键词定位与关键词＋向量定位，报告文件级 Top-1/5/10 命中率。
- [ ] C5. 比较有无定位提示对修复率、token 和耗时的影响。
- [ ] C6. 在相同预算上限下比较单轮与测试反馈修复；若要单独衡量反馈作用，使用相同轮数的无反馈对照。
- [ ] C7. 分开报告补丁产出率、独立测试验证的修复率、环境失败率、超时率、平均轮数和成本。
- [ ] C8. 逐例归档定位错误、理解错误、补丁错误、环境错误、预算耗尽等失败原因；无法确定的原因保留未知并人工复核。

### 验收

- 每个实例都能追溯到输入、版本、模型调用、补丁和独立测试结果。
- 所有计划实例均进入总表，环境失败不静默剔除；同时展示总样本口径与环境有效样本口径。
- 对有限预算或非确定性实验报告运行次数和限制，不将单次结果视为稳定收益。
- 本轮不预设成功率；先建立可信基线，再按主要失败原因选择下一项优化。
- 自建评测结果不能表述为 SWE-bench 官方成绩；官方基准接入留到后续单独立项。
